# 社内規程 × モジュール連動方針（JP）

**版:** 1.1 · **日付:** 2026-09-22  
**正本:** 本ファイル · カタログ: [catalog.yaml](catalog.yaml) · 起草: [00-起草スタイル.md](00-起草スタイル.md)

テナント施行文の最終確定は人間。パック標準は **カタログ · 雛形 · manifest · validate · モジュール有効化時の Work Order** で支える。

---

## 1. 粒度 — リスク領域単位（ハイブリッド）

**採用しない:** モジュールごとに必ず **新規** REG を作る。

**採用する:**

1. 金銭・個人情報・許認可などの **リスク領域** で規程本体をまとめる  
2. 各モジュールは `required_regulations` / `optional_regulations` で **既存 REG を参照**する  
3. 業種固有の定常オペ（医療機器 QMS/GVP 級）だけ **by-module REG** を例外的に持つ  

| リスク領域 | 標準 REG（例） | 典型モジュール |
|------------|----------------|----------------|
| 記帳 · 決算 · **資金** | REG-027 経理（資金章含む） | `jp_bank_corporate` · 会計全般 |
| 法人税等申告準備 | REG-031 | `jp_tax_corporate` |
| 消費税 · **還付** | REG-032（還付を同規程に吸収） | `jp_tax_consumption` · `jp_consumption_refund` |
| インボイス | REG-033 | `jp_invoice_qualified` |
| 源泉 · 法定調書 | REG-034 | `jp_withholding_statutory` |
| **給与計算** | REG-035 給与規程 | `jp_payroll` |
| **社会保険手続** | REG-036 社会保険手続規程 | `jp_social_insurance` |
| **許認可**（申請·台帳·民泊運用） | REG-037 許認可管理規程 | `jp_permit_application` · `jp_permit_registry` · `jp_minpaku` |
| Operator / Wire **権限** | REG-030 | 横断（金流モジュールで必須化） |
| 個人情報 | REG-010 | `jp_privacy_policy` 他（PII） |
| 内部監査 · J-SOX 評価の社内役割 | REG-016（+ REG-027 との分界） | `jp_jsox` — **専用 REG は作らない** |
| 事業オペ（宿泊等） | 既存 by-module REG | 枠（スタブ）許容。有効テナント業種だけ厚くする |

免許・許可種別が増えても REG は増やさない（許可カタログ / PER 台帳が増える）。

---

## 2. 深さのゲート

次を扱うモジュール・規程は、**厚い雛形（手続・禁止・別紙）を必須**とする。

- **金流**（記帳、資金繰り、支払、振込承認、税額・還付の社内準備）
- **個人情報**（取得・利用・保管・開示、給与・社保の個人明細）

`skeleton` の事業モジュール専用 REG は **枠（薄いスタブ）のまま**でよい。有効化したテナントの業種だけ厚くする。

---

## 3. 規程クラス（分類）

| クラス | 意味 | モジュール追加時の典型アクション |
|--------|------|----------------------------------|
| **reuse** | 既存 REG を参照するだけで足りる | `required`/`optional` を有効化 · 施行文シード |
| **thicken** | モジュール bind の雛形が薄い枠 | パック雛形の厚化草案（LLM 可）→ 人間承認 |
| **fork_family** | 隣接業種に似た規程があるが法域・義務が異なる | **共通章の参照案 + 新別紙/新 REG 草案**。**既存業種の施行文は書き換えない** |
| **new** | 当てはまる REG が無い | 新 REG 草案（リスク領域名を先に決める） |
| **none** | 規程不要（notes で理由） | Work Order に「不要」と記録のみ |

**禁止:** 医療機器 QMS（REG-025 等）を化粧品モジュール有効化のトリガで **同一規程にマージ・上書き**すること。語彙が似ていても fork_family とする。

---

## 4. モジュール追加・有効化ワークフロー

```
モジュール追加（catalog）または orgos modules activate
        ↓
決定論: regulation plan（分類 reuse/thicken/fork_family/new/none）
        ↓
Work Order 起票（Compliance · task_type implement）
        ↓
LLM: 草案のみ（パック template 差分 or テナント草案。施行確定しない）
        ↓
人間: 法務/薬事レビュー → 取締役会等で承認 → 施行文・enabled
        ↓
orgos validate（required_regulations · 施行文存在）
```

| 段階 | 主体 | 出力 |
|------|------|------|
| 分類 | CLI / lib（決定論） | `RegulationModulePlan` |
| 起票 | `modules activate`（既定オン） | `docs/reports/routing-queue/IMP-*.yaml` |
| 草案 | LLM（Work Order 実行時） | 未承認ドラフト |
| 仕上げ | 人間 | 施行文 · 版 · 施行日 |
| ゲート | `validate` | error on missing required REG |

CLI:

```bash
orgos modules regulation-plan <moduleId>   # 分類のみ（書き込みなし）
orgos modules activate <moduleId>          # 有効化 + 既定で規程 WO 起票
orgos modules activate <moduleId> --skip-regulation-wo
```

実装正本: `src/lib/regulation-module-workflow.ts`

## 5. manifest フィールド

| フィールド | 意味 |
|------------|------|
| `optional_regulations` | 関連推奨。activate で有効化候補 |
| `required_regulations` | モジュール有効時にテナントで `enabled: true` 必須（validate **error**） |

金流・PII・許認可ゲートに該当するモジュールは `required_regulations` を宣言する。  
参照が空のときは `optional_regulations: []` とし、`notes` に「規程不要」の理由を書く。

---

## 6. 有効化連動（validate）

1. モジュールが有効  
2. その manifest に `required_regulations` がある  
3. いずれかがテナントで未登録または `enabled: false`  

→ `validateRegulations` / `orgos validate` は **error**。

施行文ファイル欠落は、enabled かつ effective な REG に対して error。

---

## 7. カタログ bind

| bind | 用途 |
|------|------|
| `core` / governance | 横断（経理 · 権限 · 個人情報等） |
| `module` | 単一モジュール専属（税の 031 等） |
| `module_any` | リスク領域で複数モジュールのいずれかが有効なら bind 充足（許認可 REG-037） |
